# DiskCache Evict / Unlink NVMe 性能测试步骤

本文只保留 NVMe 服务器上的一键完整测试步骤。目标是通过 Python internal API 和 fio 基准，在同一块 NVMe 文件系统上对比纯写、纯读、纯删除、写触发 evict、读写混合、读写 evict 混合，以及 direct I/O 未对齐行为。

## 1. 测试范围

Falcon 业务测试使用 Python internal API，不经过 FUSE 挂载点。调用链路为：

```text
pyfalconfs.Client
  -> python_interface/pyfalconfs
  -> python_interface/_pyfalconfs_internal
  -> FalconCreate / FalconWrite / FalconClose / FalconUnlink / FalconRead
```

fio 只作为 NVMe 文件系统基准，不经过 Falcon。fio 结果用于判断底层盘读写上限，以及 Falcon internal API 相对底层盘的开销。

## 2. NVMe 目录要求

推荐使用实际 NVMe 盘目录作为 `BENCHMARK_ROOT`，例如：

```text
/data4/hxing
```

脚本会检查 `BENCHMARK_ROOT` 所在文件系统，并记录设备、文件系统、容量、可用空间和 inode 使用情况。测试目录必须满足：

| 要求 | 说明 |
| --- | --- |
| 有写权限 | 当前用户需要能在该目录下创建 benchmark 输出目录和 fio 文件 |
| 空间足够 | P-3/P-RWE 会按磁盘容量动态扩大写入量，用于触发 evict |
| 尽量使用 NVMe | 如果不是 NVMe，也能运行，但结果不能作为 NVMe 结论 |
| 不直接使用 `/data4` | 如果只有 `/data4/hxing` 有权限，应设置 `BENCHMARK_ROOT=/data4/hxing` |

## 3. 一键执行命令

推荐命令：

```bash
BENCHMARK_ROOT=/data4/hxing \
CLIENTS=4 \
FILES=6000 \
READ_FILES=6000 \
PINNED_READ_FILES=256 \
UNLINK_FILES=6000 \
FILE_SIZE=2097152 \
MAX_LOCAL_DISK_SIZE=16 \
FALCON_LOG_LEVEL=INFO \
WAIT_SEC=45 \
MIXED_DURATION_SEC=120 \
FIO_SIZE=2G \
FIO_LARGE_SIZE=10G \
FIO_LARGE_RUNTIME=10 \
FIO_NUMJOBS_LIST="1 4 8 16" \
bash tools/run_pyfalcon_client_benchmark.sh all
```

参数含义：

| 参数 | 含义 |
| --- | --- |
| `BENCHMARK_ROOT` | benchmark 输出目录、fio 测试目录、metadata/cache workspace 所在根目录 |
| `CLIENTS=4` | Python internal API 业务 client 数；混合场景中读写各 4 个 client |
| `FILES=6000` | 普通写入场景的基础文件数 |
| `READ_FILES=6000` | P-R1 纯读场景的读数据集文件数 |
| `PINNED_READ_FILES=256` | P-RW/P-RWE 中每个 reader 预打开并 pin 的读热集文件数 |
| `UNLINK_FILES=6000` | 主动 unlink 删除文件数 |
| `FILE_SIZE=2097152` | 单文件 2MiB |
| `MAX_LOCAL_DISK_SIZE=16` | 可选：把本轮临时 client config 的 `max_local_disk_size` 覆盖为 16GiB，用于控制 DiskCache 逻辑容量；本机快速验证可改成 `1` |
| `FALCON_LOG_LEVEL=INFO` | 可选：把本轮临时 client config 的日志级别调到 INFO，便于 summary 采集 `DiskCache::Cleanup()` 和 `CleanupForEvict()` 成功日志 |
| `WAIT_SEC=45` | P-3/P-RWE 写完后等待后台 evict 的时间窗口 |
| `MIXED_DURATION_SEC=120` | P-RW/P-RWE 固定时长持续读写窗口；reader 循环读已打开并 pin 的读热集，writer 持续写新文件 |
| `HOT_READ_LAG=128` | 保留给历史兼容参数；正式 P-RW/P-RWE 不使用 |
| `FIO_SIZE=2G` | fio 普通基准单 job 数据量 |
| `FIO_LARGE_SIZE=10G` | fio 大文件连续写数据量 |
| `FIO_LARGE_RUNTIME=10` | fio 大文件连续写运行时间 |
| `FIO_NUMJOBS_LIST` | fio 读、写、读写混合矩阵的并发数 |

## 4. 本机快速触发 evict

如需在本机用较小数据量验证后台和前台 evict，可以临时压低逻辑 cache 容量并打开 INFO 日志。后台 evict 示例：

```bash
BENCHMARK_ROOT=/tmp/pyfalcon_evict_verify \
REQUIRE_NVME=0 \
MAX_LOCAL_DISK_SIZE=1 \
FALCON_LOG_LEVEL=INFO \
CLIENTS=1 FILES=14 FILE_SIZE=67108864 WAIT_SEC=5 \
AUTO_EVICT_CONFIG=0 EVICT_THRESHOLD=0.50 \
bash tools/run_pyfalcon_client_benchmark.sh P-3
```

前台 evict 示例（为避免后台先清掉空间，这里把 `DISKCACHE_EVICTION_RATIO` 设为 0，仅用于强制验证前台路径）：

```bash
BENCHMARK_ROOT=/tmp/pyfalcon_evict_verify_fg \
REQUIRE_NVME=0 \
MAX_LOCAL_DISK_SIZE=1 \
FALCON_LOG_LEVEL=INFO \
CLIENTS=1 FILES=10 FILE_SIZE=67108864 WAIT_SEC=3 \
AUTO_EVICT_CONFIG=0 EVICT_THRESHOLD=0.50 DISKCACHE_EVICTION_RATIO=0 \
bash tools/run_pyfalcon_client_benchmark.sh P-3
```

## 5. 动态 evict 水位

不同服务器磁盘容量不同，不能固定复用同一个 evict threshold。脚本会动态读取 `BENCHMARK_ROOT` 所在文件系统的总量、已用量、可用量和 inode 使用情况，自动计算：

| 输出字段 | 含义 |
| --- | --- |
| `threshold` | 本轮设置的 DiskCache evict 水位 |
| `files` | P-3/P-RWE 为触发 evict 自动扩展后的写入文件数 |
| `write_bytes` | 预计写入字节数 |
| `used_ratio` | 当前已用比例 |
| `minimum_start_threshold` | 满足 DiskCache 启动检查所需的最低 threshold |
| `final_ratio` | 写入后预计达到的使用比例 |
| `write_ratio` | 本轮写入量占文件系统容量比例 |

这些信息会写入：

```text
$OUT_DIR/evict_config.txt
```

判断 P-3/P-RWE 是否应该触发 evict 时，优先看 `evict_config.txt`，不要只看原始 `FILES=6000`。

P-RW 为了和 P-RWE 保持同样的持续写入窗口，也会动态放大 writer 的最大写入文件数，但保持 `STORAGE_THRESHOLD=1`，避免后台 evict 介入。P-RWE 使用动态 threshold 触发后台 `DiskCache::Cleanup()`。两者都按 `MIXED_DURATION_SEC` 统计读吞吐和写吞吐。

P-RW/P-RWE 使用 pinned-read 口径：先预创建 `PINNED_READ_FILES * CLIENTS` 个读热集文件；reader 在混合阶段开始前对这些文件执行 `Open + warmup Read`，让读热集进入 DiskCache 并被 pin；writer 开始后持续写新文件，P-RWE 通过写入推动后台 `DiskCache::Cleanup()`。JSON 中应确认 `timed=true`、`read_pattern=pinned_read_set`、`pinned_read_files_per_client=PINNED_READ_FILES`、`reader.operation_error_count=0`。

当前新方案的 evict 元数据删除顺序为：`DiskCache::Cleanup()` / `CleanupForEvict()` 选中可回收 cache item 后，先通过 listener 调用服务端 `UNLINK_IF_INODE_MATCH(path, expected_inode)`；只有 metadata 条件删除返回成功，才继续删除本地 cache 文件并从 DiskCache 索引中移除。若 metadata 删除失败，本地 cache 文件保留，本轮 evict 计入 failed，用于避免“cache 已删但 metadb 仍可见”的不一致状态。

## 6. 测试 case

| 编号 | 场景 | 说明 |
| --- | --- | --- |
| P-1 | Python internal 纯写 | 4 writer client 并发 `Create/Write/Flush/Close` |
| P-2 | Python internal 纯 unlink | 先预创建，再 4 deleter client 并发 `FalconUnlink` |
| P-3 | Python internal 写触发 evict | 写入足够多文件，后台 `DiskCache::Cleanup()` 删除 cache |
| P-5 | Python internal 边写边 unlink | 4 writer client 和 4 deleter client 同时运行 |
| P-R1 | Python internal 纯读 | 预创建读数据集后 4 reader client 并发读取 |
| P-RW | Python internal pinned 读 + 写 | 4 reader client 循环读已打开并 pin 的读热集，4 writer client 持续写新文件，运行 `MIXED_DURATION_SEC` 秒，不主动触发 evict |
| P-RWE | Python internal pinned 读 + 写 + evict | 4 reader client 循环读已打开并 pin 的读热集，4 writer client 持续写新文件，运行 `MIXED_DURATION_SEC` 秒，同时写入推动后台 evict |
| P-DIO | direct I/O 对齐验证 | 对齐写、长度未对齐、offset 未对齐、buffer 未对齐 |
| B-1 - B-6 | fio 基准 | 顺序读写、多文件读写、本地删除、大文件 2MiB 连续写 |
| B-MATRIX | fio 多并发矩阵 | `numjobs=1/4/8/16` 的读、写、读写混合 |
| B-DIO | fio direct I/O 未对齐验证 | `bs=4097` 验证本地 direct 写是否返回 `EINVAL` |

## 7. 结果文件

每次执行会生成一个新的输出目录：

```text
$BENCHMARK_ROOT/pyfalcon_client_benchmark_YYYYMMDD_HHMMSS
```

测试完成后，优先回传最终整合日志：

```text
$OUT_DIR/final_report.log
```

`final_report.log` 已经整合以下内容：

| 内容 | 用途 |
| --- | --- |
| `benchmark_summary.md` | Python internal、fio、evict、direct I/O 的核心结果汇总 |
| `storage_info.txt` | `BENCHMARK_ROOT` 所在设备、文件系统、容量信息 |
| `evict_config.txt` | 动态 threshold、写入文件数、写入字节数和触发水位计算过程 |
| `python/*.json` | 每个 Python internal case 的详细耗时、吞吐和错误信息 |
| `fio/*.json` | fio 基准和多并发矩阵结果 |
| `logs/*monitor*` | P-3/P-RWE 运行期间 cache 大小、进程状态、写入字节等监控数据 |
| Falcon 日志摘要 | `DiskCache::Cleanup()`、`CleanupForEvict()`、evict 前置 metadata 条件删除的聚合结果 |

## 8. 卡住判断

如果 P-3/P-RWE 长时间没有进展，先看对应 monitor 日志。重点观察：

| 指标 | 判断方式 |
| --- | --- |
| `write_bytes` | 长时间不变说明写入侧可能已经停止 |
| `syscw` / `wchar` | 长时间不变说明进程没有继续发起写系统调用 |
| cache 目录大小 | 长时间不变说明既没有继续写入，也可能没有继续 cleanup |
| worker 进程状态 | 如果为 `Z` 或进程已经退出，需要按异常退出处理 |

如果这些指标仍在变化，说明还在持续写入或 cleanup，不应直接判断为卡住。

## 9. NVMe 结果记录口径

结果文档只记录 NVMe 服务器实测结果。每次补充新结果时，至少需要写清楚：

| 项目 | 说明 |
| --- | --- |
| 测试时间 | `final_report.log` 中的生成时间 |
| 输出目录 | `$OUT_DIR` |
| 存储设备 | `storage_info.txt` 中的设备和文件系统 |
| Python internal 吞吐 | P-1/P-2/P-3/P-5/P-R1/P-RW/P-RWE；P-RW/P-RWE 必须确认 `timed=true` 和 `read_pattern=pinned_read_set` |
| evict 聚合 | cleanup/remove 吞吐、轮次、删除文件数、删除数据量、时延 |
| metadata 条件删除 | enqueued、processed、succeeded、failed、batch calls、max batch、p99、max latency；当前实现为 evict 前先执行 `UNLINK_IF_INODE_MATCH(path, expected_inode)`，成功后再删除本地 cache |
| fio 基准 | B-1 - B-6 和 B-MATRIX |
| direct I/O | P-DIO 和 B-DIO 的实际返回值 |
