# DiskCache Evict 性能测试结果对比

本文对比当前方案批量化 metadata 条件删除前后的 NVMe 服务器测试结果。两轮均使用 `/data4/hxing`，底层设备为 `/dev/nvme0n1`，文件系统为 `ext4`，Python internal API 场景均为 `CLIENTS=4`，单文件 `2MiB`，混合场景固定运行 `120s`，fio 并发矩阵为 `numjobs=1 4 8 16`。

| 批量化前 | `commitcomment-188227778` | 2026-06-10 03:02:17 | `/data4/hxing/pyfalcon_client_benchmark_20260610_024302` | evict 前置 `UNLINK_IF_INODE_MATCH`，逐条 metadata 条件删除 |
| 批量化后 | `commitcomment-188256546` | 2026-06-10 09:13:06 | `/data4/hxing/pyfalcon_client_benchmark_20260610_085359` | evict 前置 `UNLINK_IF_INODE_MATCH`，按 metadata worker 分组批量条件删除 |

## 1. 核心结论

| 项目 | 批量化前 | 批量化后 | 判断 |
| --- | ---: | ---: | --- |
| P-3 写触发 evict 写吞吐 | 927.26 MiB/s | 1141.47 MiB/s | 提升约 `23.1%` |
| P-3 cleanup 吞吐 | 822.85 MiB/s | 3329.36 MiB/s | 提升约 `4.0x` |
| P-3 remove 吞吐 | 1614.16 MiB/s | 3448.32 MiB/s | 提升约 `2.1x` |
| P-RWE writer 吞吐 | 971.29 MiB/s | 1190.09 MiB/s | 提升约 `22.5%` |
| P-RWE cleanup 吞吐 | 709.98 MiB/s | 3515.42 MiB/s | 提升约 `5.0x` |
| P-RWE reader 吞吐 | 3417.05 MiB/s | 3662.07 MiB/s | 略升，读路径稳定 |
| Python internal 业务错误 | 0 | 0 | 两轮业务均无错误 |
| evict failed/scanned | 16486 / 154370 | 0 / 152802 | 批量化后本轮没有 evict failed |

批量化后的结果更符合预期：evict cleanup 吞吐已经显著高于写入吞吐，因此边写边 evict 时具备把 cache 使用量压回水位线以下的吞吐余量。批量化前 cleanup 吞吐低于或接近 writer 吞吐，持续写入时更容易出现水位下降慢的问题。

| --- | ---: |
| attempted / processed / succeeded | 145634 / 145634 / 145634 |
| failed / dropped | 0 / 0 |

## 6. 最终判断

批量化 metadata 条件删除后，当前方案已经验证出三个关键结果：

| 结论项 | 说明 |
| --- | --- |
| 功能正确性 | P-3/P-RWE/P-RW/P-2 等业务场景均 `error_count=0`，metadata 条件删除 `failed=0`。 |
| 删除吞吐 | P-3 cleanup `3329 MiB/s`、P-RWE cleanup `3515 MiB/s`，均明显高于对应 writer 吞吐。 |
| 瓶颈变化 | metadata RPC/元数据路径已经不是主要瓶颈，后续优化应关注本地 cache remove、cleanup round 调度粒度、以及 Falcon 写路径本身。 |

与批量化前相比，最关键的改进是 evict 删除吞吐已经从低于/接近写入吞吐，提升到写入吞吐的约 3 倍。这意味着持续写入触发后台 evict 时，cleanup 有能力把 cache 使用量往水位线以下拉回。
